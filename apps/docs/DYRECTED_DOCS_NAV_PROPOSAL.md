# Dyrected Docs Navigation Proposal

This file defines the new Dyrected documentation navigation structure.

It is based on Payload's top-level grouping model, with one intentional addition:

1. Basics
2. Quick Start Guides
3. Managing Data
4. Features
5. Ecosystem
6. Deployment

The key decision is that `Quick Start Guides` becomes a first-class top-level group instead of being buried under `Basics` or `Getting Started`.

Date: `2026-07-08`

## Reference model

Payload's top-level groups are:

1. Basics
2. Managing Data
3. Features
4. Ecosystem
5. Deployment

Dyrected should keep that overall shape, but insert `Quick Start Guides` between `Basics` and `Managing Data`.

Reference material generated by `@dyrected/knowledge` should usually be embedded into the concept or task pages that already explain that area, instead of living in a large separate reference tree.

## Sidebar behavior

- top-level groups are always visible
- each group contains accordion topics
- opening one topic closes sibling topics in the same group
- pages appear only when a topic is expanded

This should feel very close to Payload's docs navigation.

## Why this structure works

- It keeps Payload's top-level mental model intact.
- It adds one Dyrected-specific entry group for onboarding by user type and framework.
- It avoids introducing extra top-level groups for concerns that Payload already contains successfully inside `Basics`, `Managing Data`, or `Features`.
- It gives quickstarts enough prominence to become a primary entry path instead of a side topic.
- It avoids duplicating concepts across separate concept pages and reference pages.
- It lets `@dyrected/knowledge` generated reference material live inside the pages that already explain the concept, which should make docs feel more complete and less fragmented.

## Generated reference strategy

Generated reference material should be embedded into the page that already owns the concept whenever possible.

### Reference page mapping

Current generated/reference-heavy pages from the old docs should move like this:

| Old reference page | New canonical home | Notes |
| --- | --- | --- |
| `Reference > API Reference` (`reference/introduction.mdx`) | `Managing Data > SDK API > Overview` and `Managing Data > REST API > Overview` | Split the current mixed introduction. Do not keep one page that introduces both if the new nav separates them. |
| `Reference > Configuration Reference` (`reference/configuration.mdx`) | `Basics > Configuration > Overview` plus the relevant child pages | Keep prose in the overview, then embed generated config contracts into `overview`, `collections`, `globals`, `environment-variables`, and later any admin/storage/email pages if they are added. |
| `Reference > Field Types Reference` (`reference/fields.mdx`) | `Basics > Fields > Overview` plus each field page | Shared field contract material belongs in `overview`; field-specific generated material should be embedded into `array`, `blocks`, `checkbox`, `code`, `date`, `relationship`, `upload`, and the other field pages. |
| `Reference > SDK Reference` (`reference/sdk.mdx`) | `Managing Data > SDK API` | Keep the overview in `sdk-api/overview`, then split generated method/reference sections into `sort`, `filter`, `depth`, `pagination`, and add more SDK subpages later if the generated surface grows beyond those topics. |
| `Reference > REST API Reference` (`reference/rest-api.mdx`) | `Managing Data > REST API > Overview` | Keep the base URL, auth, filtering, errors, and route-family reference here. If this grows, later split into collections/globals/auth/upload child pages under `Managing Data > REST API`. |
| `Reference > OpenAPI Specification` (`reference/openapi.mdx`) | Standalone generated artifact linked from `Managing Data > REST API > Overview` | This is one of the few things that can remain separate because it is a true machine-oriented lookup artifact. It does not need to become a top-level nav group. |
| `Reference > Workflow Reference` (`reference/generated-workflows.mdx`) | `Features > Versions`, `Features > Authentication`, and workflow-focused concept/feature pages as needed | Do not keep workflow contracts isolated if the reader learns workflows elsewhere. Embed generated transition/state/capability reference into the page that explains the workflow feature, or create a feature-owned workflow page later if workflows become first-class in the new nav. |

### How to place generated material inside the new docs

- `Basics > Configuration > Overview`
  Generated top-level config contract, `defineConfig`, and shared config object reference.
- `Basics > Configuration > Collections`
  Generated collection config contract and collection-specific options.
- `Basics > Configuration > Globals`
  Generated global config contract and global-specific options.
- `Basics > Configuration > Environment Variables`
  Generated env var reference if `@dyrected/knowledge` exposes it cleanly.
- `Basics > Fields > Overview`
  Shared field options, common properties, admin options, and cross-field rules.
- `Basics > Fields > [field-name]`
  Field-specific generated options, types, and examples for each field page.
- `Managing Data > SDK API > Overview`
  SDK client creation, shared query arguments, error model, and top-level contracts.
- `Managing Data > SDK API > Sort|Filter|Depth|Pagination`
  Generated detail for each query concern.
- `Managing Data > REST API > Overview`
  Base URL, auth headers, route families, filtering, errors, and links to OpenAPI.

### Standalone artifacts that can stay separate

- runtime OpenAPI schema docs
- code generation guidance based on OpenAPI
- any generated contract index whose main audience is tooling rather than human readers

This keeps the navigation focused on reader intent while still preserving full generated reference depth where it is useful.

## Best-fit data model

```ts
type DocumentationPage = {
  title: string
  slug: string
}

type DocumentationTopic = {
  title: string
  slug: string
  pages: DocumentationPage[]
}

type DocumentationGroup = {
  title: string
  slug: string
  topics: DocumentationTopic[]
}

type DocumentationNav = DocumentationGroup[]
```
