Authentication in Dyrected is opt-in and lives on your collections. You turn a collection into a login provider by adding one line — `auth: true` — and Dyrected gives you email and password fields, a full set of login endpoints, and stateless JWT sessions you can check anywhere in your app.

By the end of this page you should understand what `auth: true` actually does, how a session works, where roles and access control fit, and how to keep your dashboard logins separate from your application's users. This is the home page for the concept; deeper mechanics live on their own pages, linked as you go.

## The mental model

An **auth collection** is just a normal collection with a login attached. When you set `auth: true`, three things happen:

1. **Fields are injected.** Every document gets an `email` (required, unique) and a `password` (hashed on save, never returned in API responses). A `roles` field is added too, so you have somewhere to store permissions from day one.
2. **Endpoints are mounted.** A full set of auth routes appears under `/api/collections/{slug}/` — login, logout, the current user, password reset, invitations, and more.
3. **Sessions become available.** On login, the server signs a JSON Web Token (JWT — a signed token the client holds to prove who is logged in) and hands it back. You send it on future requests, and Dyrected turns it back into a `user` you can read in access rules and hooks.

You can enable auth on as many collections as you like. A common shape is one collection for your application's members and a separate one for the people who log into the CMS dashboard.

## Enable it

Add `auth: true` to any collection. You declare only the extra fields you want — `email`, `password`, and `roles` are added for you, so you never list them yourself:

```ts
// dyrected.config.ts
import { defineCollection } from '@dyrected/core'

export const Users = defineCollection({
  slug: 'users',
  auth: true,
  fields: [
    { name: 'name', label: 'Name', type: 'text' },
  ],
})
```

That single collection now has working login endpoints. Before anyone can log in, set the signing secret Dyrected uses to sign session tokens:

```bash
# .env.local
DYRECTED_JWT_SECRET=a-long-random-secret-at-least-32-chars
```

The same secret must be present in every environment, and it must not be empty — auth collections throw at startup if `DYRECTED_JWT_SECRET` is missing. Changing it invalidates every existing session at once.

## What you get

Enabling auth injects these fields into the collection. You can redefine them to add labels or admin options, but their core constraints are always enforced:

| Field | Type | Notes |
| --- | --- | --- |
| `email` | `email` | Required, unique. This is the login identifier and cannot be changed after the document is created. |
| `password` | `text` | Required, hashed on save, stripped from every API read response. A user can only change their own. |
| `roles` | `select` | Options `admin`, `editor`, `viewer` by default; starts empty. Only an existing admin can change another user's roles. |

And it mounts a full set of endpoints under `/api/collections/{slug}/` — `login`, `logout`, `me`, `refresh-token`, `forgot-password`, `reset-password`, `invite`, `accept-invite`, plus `init` and `first-user` for bootstrapping the very first account. Each one, with its exact request and response shape, is documented in [Operations](/new-docs/features/authentication/operations).

## Log in and read the user

Logging in exchanges an email and password for a token and the user record. Store the token, attach it to future requests, and Dyrected resolves it back into the signed-in user. Here it is with the SDK:

```ts
import { createClient } from '@dyrected/sdk'

const client = createClient({ baseUrl: process.env.NEXT_PUBLIC_DYRECTED_URL! })

// Exchange credentials for a session
const { token, user } = await client.collection('users').login(
  'jane@example.com',
  'hunter2',
)

// Tell the client to send this token on future requests
client.setToken(token)

// Now protected calls work
const me = await client.collection('users').me()
```

The SDK holds the token in memory only — it does not persist it for you. Deciding *where* the token lives between requests (a cookie, storage, a framework composable) is the job of the [Cookie Strategy](/new-docs/features/authentication/cookie-strategy) page.

## Sessions are stateless

Dyrected auth has no server-side sessions. The signed token *is* the session. Every request carries it in the `Authorization` header:

```
Authorization: Bearer <token>
```

The server verifies the token on each request and, when a database is connected, re-loads the user's current document so your access rules always see fresh data. There is nothing to invalidate on the server at logout — the client discards the token and it expires on its own (after 7 days by default).

Two pages go deeper here:

- [JWT Strategy](/new-docs/features/authentication/jwt-strategy) — how the token is signed, the secret, expiry, and how another service can verify a Dyrected token.
- [Token Data](/new-docs/features/authentication/token-data) — exactly what the token carries, and how the full `user` object gets assembled for your access functions.

## Roles and access control

The injected `roles` field is where permissions live, but Dyrected does not enforce any role meaning on its own. Roles only matter when an access function reads them. The signed-in user is available as `user` in every access rule and hook:

```ts
export const Orders = defineCollection({
  slug: 'orders',
  access: {
    read: ({ user }) => !!user,
    create: ({ user }) => !!user,
    update: ({ user }) => user?.roles?.includes('admin'),
  },
  fields: [
    { name: 'total', label: 'Total', type: 'number' },
  ],
})
```

`user.roles` is available here even though the token itself does not carry roles — Dyrected re-hydrates the user from the database on each request. For the full model, see [Access Control](/new-docs/basics/access-control/overview).

## Multiple auth collections and the dashboard

You can have more than one auth collection, and they are completely independent — separate endpoints, separate tokens, separate sessions. Someone logged into your storefront as a `customer` has no relationship to whoever can log into the CMS.

Dyrected treats one slug specially: **`__admins`**. When a collection with that slug exists, it becomes the sole login gateway for the dashboard. Any other auth collection powers your application, not the CMS. This is how you keep customer accounts from ever reaching the admin panel. The full walkthrough — including onboarding your first editors — lives in [Handing Off to Editors](/new-docs/features/authentication/handing-off-to-editors).

## Dashboard sign-in and SSO

Everything above describes **collection auth**: local email and password login for your application's users (and, by default, for the dashboard). Dyrected also supports **external sign-in for the dashboard** through an `adminAuth` configuration, so admins can log in with an identity provider (OIDC) or a custom JWT provider instead of a local password.

This is a separate system from collection auth — it only governs who reaches the CMS, uses its own routes under `/api/admin/auth/`, and does not change how your application's users log in. If your team needs single sign-on for the admin panel, see [Admin SSO](/new-docs/features/authentication/admin-sso) for the full setup with Okta, Azure AD, Google, or any OIDC provider.

## Programmatic access

For server-to-server calls, you have two distinct things, and it helps to keep them straight:

- **A user session** — obtained by logging a real user in (`login` → JWT) and sent as `Authorization: Bearer <token>`. Use this when a request should act *as a specific user* and respect that user's access rules.
- **A project credential** — the `DYRECTED_API_KEY` you configure for the SDK, sent as the `x-api-key` header. This identifies your *application* to the Dyrected backend. It is not a per-user login and does not stand in for a user session.

Dyrected does not currently offer per-user API keys (a key that authenticates as one specific account). If you need that today, log the user in and reuse the returned token.
