Use this page when the Next.js integration, schema, render path, and first preview flow already work and you are ready to hand the system to someone other than the person who built it.

By the end, you should know which accounts editors use, what the quickest safe handoff looks like, and where the current quick-start starter stops so you do not promise a smoother onboarding flow than the project actually ships today.

This is the last page in the quick-start sequence. It assumes the earlier setup pages are already complete and closes the loop by testing the handoff with a real editor account.

## The first handoff rule

Do not invite anyone until one real content edit already makes it from Dyrected into the frontend.

That is the real success signal. If the builder cannot make one edit and see it appear on the site, an editor should not be the person discovering what is still broken.

## Which accounts the dashboard uses

The current Next.js starter creates a reserved `__admins` collection as the dashboard login gateway.

That collection is where dashboard users live by default. The first user created through the initial setup flow becomes an admin automatically.

## Start with the right handoff model

The first editor handoff is different depending on where the admin is running:

- **Dyrected Cloud:** add team members by invitation
- **Self-hosted admin:** create the user directly in your own admin

This page treats those as two different operational paths, because the first handoff experience is not the same.

## What the self-hosted starter gives you today

In the current `dyrected init` starter, the generated `__admins` collection includes a `roles` field with these scaffolded options:

- `admin`
- `editor`

Use that starter shape as the source of truth for the self-hosted quick start. If you need more roles later, add them deliberately in your own schema instead of assuming the scaffold already created them.

For Cloud, do not assume the same role field is currently part of the team-management flow. If you are documenting the Cloud path, keep the focus on invitations rather than on editing roles in the hosted product for now.

## Recommended first handoff

### Dyrected Cloud

For Cloud, the practical first handoff is:

1. Make sure the site, preview flow, and content routes already work.
2. Invite the team member through the Cloud flow.
3. Have them complete one real edit.
4. Confirm that the edit reaches the frontend as expected.

Right now, that invitation flow is the important path to teach for Cloud.

### Self-hosted admin

For self-hosted admin, keep it simple:

1. Create the first admin account yourself.
2. Confirm the editor route, content route, and preview route all work.
3. Add one additional user in the `__admins` collection and give them the least powerful role you actually expose in your schema.
4. Watch them complete one real edit before you widen access.

This is slower than bulk onboarding, but it catches schema and permission mistakes while the system is still easy to correct.

## What to say about invites

Cloud already depends on invitations for adding team members, so the invite flow is not just an edge case there.

Self-hosted is different. Today, the clearer quick-start path is to create the user directly in the admin and test the account immediately. A fuller invite flow for self-hosted admin is planned for a later release, so this page should not imply that self-hosted onboarding already depends on invitations.

## Permission boundaries to think about early

Before handing the site over, decide:

- who can change schema versus content
- who can publish or only draft
- who should be able to edit shared globals such as navigation and settings

Those decisions do not have to become a full workflow system on day one, but they do need to be explicit. A vague "the client will probably only edit pages" is not a permission model.

## Recommended path

For most first handoffs:

- keep admin access limited
- use invitations for Cloud
- create the first additional account directly in self-hosted admin
- only mention roles where your self-hosted schema actually exposes them
- test pages, globals, and preview before widening access

The goal is confidence, not speed.

## Known quick-start edge

Some broader docs in the repo describe a scaffolded auth role set that includes `viewer`. This page keeps the quick start narrower:

- for self-hosted starter output, use the current `admin` and `editor` role shape
- for Cloud, focus on the invitation flow instead of role editing

## Success check

You are ready to call the quick start review-ready when:

- the first admin account works
- one additional editor account can complete a real content task
- the frontend and preview experience behave correctly under that account

At that point, you have moved past setup and into normal product-specific documentation and permission design.
