MongoDB is the adapter to choose when you want document-oriented storage. Install `@dyrected/db-mongodb`, give it a connection URL and a database name, and pass it as the `db` key in `dyrected.config.ts`.

```ts
import { defineConfig } from '@dyrected/core'
import { mongodbAdapter } from '@dyrected/db-mongodb'

export default defineConfig({
  db: mongodbAdapter({
    url: process.env.DATABASE_URL!,
    dbName: process.env.MONGODB_DB_NAME || 'dyrected',
  }),
  collections: [],
  globals: [],
})
```

Set `DATABASE_URL` to a standard connection string (for example `mongodb://localhost:27017/dyrected`) and `MONGODB_DB_NAME` to the database to use within it. These are the same variable names `dyrected init` scaffolds, so a generated project already has them wired up. On startup Dyrected connects and is ready to read and write. This works with self-managed MongoDB and managed services like MongoDB Atlas.

> **Dyrected Cloud manages the database for you.** You only configure a `db` adapter when you self-host. Cloud projects normally omit `db`. See the [Database overview](/docs/deployment-and-operations/infrastructure/database/overview).

## Configuration

The MongoDB adapter takes two options:

```ts
mongodbAdapter({
  url: process.env.DATABASE_URL!,
  dbName: process.env.MONGODB_DB_NAME || 'dyrected',
})
```

| Option | Description |
| --- | --- |
| `url` | The MongoDB connection string. Read from `DATABASE_URL`. |
| `dbName` | The database to use within that connection. Read from `MONGODB_DB_NAME`, defaulting to `dyrected`. |

## How your data is stored

Each collection maps to a MongoDB collection named `collection_<slug>`, and your documents are stored natively as BSON. Dyrected maps Mongo's `_id` to the `id` field your app and API work with. New documents get the same string IDs as the SQL adapters (a prefixed NanoID by default, or whatever `idType` and `idPrefix` you configure), not MongoDB `ObjectId`s. Globals are stored in a `dyrected_globals` collection.

Because MongoDB is schema-flexible, there are no tables to create and no columns to add. Two ideas that matter on the relational adapters don't apply here:

- **Field promotion is a no-op.** `promoted: true` exists for SQL adapters that store documents in a JSON column; MongoDB already stores every field natively, so there's nothing to promote.
- **There are no columns to sync.** Adding a collection or field needs no migration step because MongoDB doesn't enforce a table shape. Startup sync only creates the indexes you declare (see below).

That flexibility doesn't remove the need to keep your content contract compatible. Renamed fields, new defaults, and changed shapes still have to line up with the documents already in your database. See [Migrations](/docs/deployment-and-operations/infrastructure/database/migrations) for the field-level tools that handle this.

## Query performance and indexes

Since there are no promoted columns, query performance comes from MongoDB's own indexes. On startup Dyrected creates the indexes you declare: a unique index for each `unique: true` field, and one for each entry in a collection's `indexes` array, including compound ones. For anything else that gets slow on a large collection, add the index directly in MongoDB (for example with `createIndex` or MongoDB Compass) against the `collection_<slug>` collection. See [Indexes](/docs/deployment-and-operations/infrastructure/database/indexes) for how this compares to field promotion on the SQL adapters.

The `unique: true` field option is enforced by a real unique index. A duplicate write fails with a `DuplicateKeyError` (HTTP 409), the same as on the SQL adapters. See [Enforcing uniqueness](/docs/deployment-and-operations/infrastructure/database/indexes#enforcing-uniqueness).

`increment`, `decrement` and conditional `where` updates run as a single atomic `findOneAndUpdate`, so they are safe under concurrent writes. `lock: 'for-update'` has no effect on MongoDB: inside a transaction, MongoDB already locks the documents a write touches, and the driver retries the transaction if two writers conflict.

## Transactions

The MongoDB adapter supports transactions using MongoDB sessions, and workflow transitions rely on them. One requirement to plan for: **multi-document transactions require a replica set or sharded cluster.** A standalone `mongod` cannot run them. MongoDB Atlas and most managed offerings already run as replica sets, so this usually only bites on a bare local `mongod`. See [Transactions](/docs/deployment-and-operations/infrastructure/database/transactions).
