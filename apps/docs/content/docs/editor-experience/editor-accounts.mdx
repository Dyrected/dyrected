This page helps you put authentication in the right place before you build around it.

Dyrected has two kinds of login, and they never mix:

- **Editor login** controls who can enter the dashboard: owners, teammates, clients, editors, and administrators.
- **Application-user login** controls who can sign in to your product: customers, members, and anyone else your app authenticates. You add it with an `auth` collection.

Both **Dyrected Cloud** and **self-hosted Dyrected** support both kinds. The difference is who manages editor login. On Cloud, Dyrected manages dashboard access for you. Self-hosted projects manage it themselves.

<CloudOnly>

## Editor login is workspace access

Think about Dyrected Cloud the way you would think about a managed content workspace. You invite the people who should edit content, publish changes, manage media, and work inside the CMS. Dyrected handles access to that workspace and the hosted content backend behind it.

Use Cloud workspace access for:

- site owners who manage the content workspace
- clients and editors who update approved content
- team members who need dashboard access
- workspace access to the hosted content API and media library

Editors sign in through Dyrected Cloud. You do not create passwords for them in your own schema.

## Application-user login on Cloud

Mark any collection in your schema with `auth: true` and it becomes a login collection for your application, on Cloud as well as self-hosted. Cloud keeps that collection as you defined it, including its access rules, and does not mix it with the dashboard.

```ts
// dyrected.config.ts
import { defineCollection } from "@dyrected/core";

export const Customers = defineCollection({
  slug: "customers",
  auth: true,
  fields: [{ name: "name", label: "Name", type: "text" }],
});
```

Application-user login uses the same auth collection model, endpoints, and `user` object in access rules as self-hosted Dyrected. The collection auth endpoints, request shapes, and SDK methods are documented in [Operations](/docs/deployment-and-operations/authentication/operations).

## How Cloud picks the dashboard collection

Cloud has to decide which collection in your schema represents dashboard accounts. It checks in this order and uses the first match:

1. A collection with the slug **`__admins`**.
2. The collection named by `adminAuth.collectionSlug`, if it exists in your schema.
3. The first collection in your schema that has `auth` enabled.

The collection Cloud picks is replaced with a Cloud-managed one. Its slug becomes `accounts`, its access becomes admin-only, and its `roles` options become `admin`, `editor`, `viewer`, and `owner`. Your other fields on it are kept.

<Warning>

**Define `__admins` before you add application-user auth collections.** If your schema has an auth collection such as `customers` and no `__admins`, rule 3 selects `customers` as the dashboard collection. Cloud then renames it and locks it to admins, and your customers can no longer log in through it.

</Warning>

Add an `__admins` collection with `auth: true`, and Cloud always uses it. Every other auth collection then stays an application-user collection:

```ts
export const Admins = defineCollection({
  slug: "__admins",
  auth: true,
  fields: [{ name: "name", label: "Name", type: "text" }],
});
```

Cloud still manages who can sign in to the dashboard. The `__admins` collection only tells Cloud which collection should carry that role and field shape.

## What a Cloud handoff should prove

Before inviting a client or teammate, make sure one real content edit already flows from Dyrected Cloud into the frontend. That is the handoff signal that matters.

The first handoff usually looks like this:

1. Create or connect the Cloud site.
2. Sync the schema so the hosted content backend knows your collections and globals.
3. Confirm the frontend can read published content.
4. Invite the editor or client into the Cloud workspace.
5. Ask them to make one safe edit and confirm it reaches the site.

Use [Handing Off to Editors](/docs/editor-experience/hand-off-to-editors) for the full onboarding checklist.

## What stays in your application

Auth collections give you accounts and login. They do not replace the rest of your product. Keep these in your app or the system built for them:

- payments, checkout, carts, and orders
- subscriptions and billing
- tenant membership and product-specific permissions beyond what your access rules express

If you already use an identity provider for your product, you can keep using it. Auth collections are an option, not a requirement.

## Self-hosted collection auth

Authentication in self-hosted Dyrected is opt-in and lives on your collections. Turn a collection into a login provider with `auth`, and Dyrected adds the fields, routes, and session behavior needed to use those documents as real accounts.

Use this path when Dyrected is part of your application backend and should own one or more account collections.

## What enabling `auth` does

An **auth collection** is a normal collection with login attached. When you enable `auth`, three things happen:

1. **Fields are injected.** Every document gets an `email` field and a `password` field. The email is required and unique. The password is hashed on save and never returned in API responses.
2. **Endpoints are mounted.** Auth routes appear under `/api/collections/{slug}/` for login, logout, the current user, password reset, invitations, and related flows.
3. **Sessions become available.** On login, the server signs a JSON Web Token (JWT) and returns it. Future requests send that token, and Dyrected turns it back into a `user` that access rules and hooks can read.

You can enable auth on more than one collection. A common shape is one collection for application members and a separate `__admins` collection for people who can log into the CMS dashboard.

## Start with `auth: true`

Add `auth: true` to a collection when you want the default setup. You declare only the extra fields you want:

```ts
// dyrected.config.ts
import { defineCollection } from "@dyrected/core";

export const Users = defineCollection({
  slug: "users",
  auth: true,
  fields: [{ name: "name", label: "Name", type: "text" }],
});
```

That collection now has working login endpoints.

Before anyone can log in, set the signing secret Dyrected uses for session tokens:

```bash
# .env.local
DYRECTED_JWT_SECRET=a-long-random-secret-at-least-32-chars
```

The same secret must be present in every environment, and it must not be empty. Auth collections throw at startup if `DYRECTED_JWT_SECRET` is missing. Changing it invalidates existing sessions.

## Tune auth only when you need to

The recommended path is still `auth: true`. Reach for an object only when you need to change built-in behavior.

The most common options to tune are login lockout and the administrative role name:

```ts
export const Admins = defineCollection({
  slug: "admins",
  auth: {
    adminRole: "super_admin", // Defaults to 'admin'
    maxLoginAttempts: 5,
    lockTime: 15 * 60 * 1000, // 15 minutes
  },
  fields: [{ name: "name", label: "Name", type: "text" }],
});
```

- `maxLoginAttempts` controls how many bad passwords Dyrected allows before locking the account.
- `lockTime` controls how long that lock lasts, in milliseconds.
- `adminRole` customizes the administrative role name (defaults to `'admin'`). Use this if your team uses custom role naming such as `'super_admin'` or `'manager'`, so the initial account setup (`/first-user`) and Admin UI privilege checks grant and recognize your custom role.

This protects the account itself. It does **not** replace host-level rate limiting, WAF rules, or proxy throttling for public routes. Keep those in place too, especially for auth, uploads, and preview endpoints. The deployment side of that lives in [Preventing Abuse](/docs/deployment-and-operations/production/preventing-abuse).

## Know what Dyrected injects

Enabling auth injects these fields into the collection. You can redefine them to add labels or admin options, but their core constraints are always enforced:

| Field | Type | Notes |
| --- | --- | --- |
| `email` | `email` | Required and unique. This is the login identifier. |
| `password` | `text` | Required, hashed on save, and stripped from API read responses. |
| `roles` | `select` | Available by default so you have somewhere to store permissions from day one. |

If you declare `roles` yourself on an auth collection, keep it as a multi-value field. Dyrected treats `user.roles` as an array of strings in access rules, workflow capability checks, and admin auth flows.

Dyrected also mounts auth endpoints under `/api/collections/{slug}/`: `login`, `logout`, `me`, `refresh-token`, `forgot-password`, `reset-password`, `invite`, `accept-invite`, `init`, and `first-user`. Each request and response shape is documented in [Operations](/docs/deployment-and-operations/authentication/operations).

## Understand the session model

Dyrected uses signed bearer tokens backed by a server-side session record. Every successful login creates a session and returns a JWT that points at it.

That means three useful things are true at once:

- clients send a normal `Authorization: Bearer <token>` header
- the server re-hydrates the live user document on each request
- logout, password reset, and password change can revoke the session immediately

Tokens still expire on their own after 7 days by default, but there is a real server-side invalidation point too.

## Log in and read the user

```ts
import { createClient } from "@dyrected/sdk";

const client = createClient({ baseUrl: process.env.NEXT_PUBLIC_DYRECTED_URL! });

const { token, user } = await client
  .collection("users")
  .login("jane@example.com", "hunter2");

client.setToken(token);

const me = await client.collection("users").me();
```

The SDK holds the token in memory only. Deciding where the token lives between requests is the job of the [Cookie Strategy](/docs/deployment-and-operations/authentication/cookie-strategy) page.

## Use roles in access control

The injected `roles` field is where permissions can live, but Dyrected does not enforce any role meaning on its own. Roles only matter when an access function reads them:

```ts
export const Orders = defineCollection({
  slug: "orders",
  access: {
    read: ({ user }) => !!user,
    create: ({ user }) => !!user,
    update: ({ user }) => user?.roles?.includes("admin"),
  },
  fields: [{ name: "total", label: "Total", type: "number" }],
});
```

`user.roles` is available here even though the token itself does not carry roles. Dyrected re-hydrates the user from the database on each request. For the full model, see [Access Control](/docs/model-content/content-rules/access-control/overview).

## Separate application users from dashboard users

You can have more than one auth collection, and they are independent: separate endpoints, separate tokens, separate sessions. Someone logged into your storefront as a `customer` has no relationship to whoever can log into the CMS.

Dyrected treats one slug specially: **`__admins`**. When a collection with that slug exists, it becomes the sole login gateway for the dashboard. Any other auth collection powers your application, not the CMS. This is how you keep customer accounts from reaching the admin panel.

The full walkthrough lives in [Handing Off to Editors](/docs/editor-experience/hand-off-to-editors).

## Know where dashboard SSO fits

Everything above describes **collection auth**. Dyrected also supports external sign-in for the dashboard through `adminAuth`, so admins can log in with an identity provider or custom JWT provider instead of a local password.

This is separate from collection auth. It only governs who reaches the CMS and uses routes under `/api/admin/auth/`. If your team needs single sign-on for the admin panel, see [Admin SSO](/docs/deployment-and-operations/authentication/admin-sso).

## Keep user sessions and project credentials separate

For server-to-server calls, keep two concepts separate:

- **A user session** is obtained by logging a real user in and sent as `Authorization: Bearer <token>`.
- **A project credential** is the `DYRECTED_API_KEY` configured for the SDK and sent as the `x-api-key` header.

The project credential identifies your application to the Dyrected backend. It is not a per-user login and does not stand in for a user session.
