Use this page when your site integration, schema, render path, and first preview flow already work, and you are ready to give someone else access.

By the end, you should know what the safest first editor handoff looks like for your runtime.

This page is intentionally shared across frameworks. The onboarding decision is not really about Next.js, Nuxt, Vue, or React. It is about where the admin is running and how new people get into it.

## The first handoff rule

Do not onboard anyone until one real content edit already makes it from Dyrected into the frontend.

That is the success signal that matters most. If the builder cannot make one edit and see it appear on the site, an editor should not be the person discovering what is still unfinished.

<CloudOnly>

## Cloud handoff

Use the Cloud path when the project is connected to a hosted Dyrected site and the team will log in through the Cloud-managed workspace.

The practical first handoff is:

1. Make sure the site, preview flow, and content routes already work.
2. Invite the team member through the [Cloud Dashboard](https://app.dyrected.com/settings/team).
3. Have them complete one real content edit.
4. Confirm that the edit reaches the frontend as expected.

For Cloud, teach the invitation flow. That is how team members enter the managed content workspace.

## Cloud account boundary

Cloud accounts are for the people working inside Dyrected: owners, teammates, clients, editors, and administrators.

Do not use Cloud workspace access as customer login for your app. If the product has members, buyers, subscribers, tenants, or account-specific dashboards, keep that authentication in the product app or identity provider that already owns it.

## Cloud handoff checklist

Before a real client handoff:

- make sure the schema has synced successfully
- confirm the frontend reads published Cloud content
- confirm preview works if the project uses preview
- invite one editor first, not the whole team
- ask that editor to make one small safe edit
- verify the edit reaches the site

## Self-hosted admin handoff

Use the self-hosted path when the Dyrected backend and admin are running inside your own application.

The current starter creates a reserved `__admins` collection as the dashboard login gateway. That collection is where dashboard users live by default for self-hosted setups. The first user created during the initial setup flow becomes an admin automatically.

The practical first handoff is:

1. Create the first admin account yourself.
2. Confirm the admin route, content route, and preview route all work.
3. Invite the next editor from the auth-backed admin collection, instead of typing their password in manually.
4. Give them the least powerful role your schema actually exposes, if your auth collection has a selectable role field.
5. Watch them complete one real edit before you widen access.

This is slower than bulk onboarding, but it catches schema and permission mistakes while the system is still easy to correct. It also matches the current self-hosted admin flow more closely: the admin sends the invite from the list view, can copy the invite URL if needed, sees invited users in the list immediately as pending users, and lets the invited person set their own password when they accept.

## What the starter gives you today

In the current `dyrected init` starter, the generated `__admins` collection includes a `roles` field with these scaffolded options:

- `admin`
- `editor`

Use that starter shape as the source of truth for the first self-hosted handoff. If you need more roles later, add them deliberately in your own schema instead of assuming the scaffold already created them.

If your auth collection defines a selectable role field with fixed options, the invite dialog can assign that role before acceptance. If your schema does not expose a clean selectable role field, keep the handoff simple and adjust roles after acceptance.

## Email is part of the handoff, not an optional polish step

For a real client or editor handoff, treat backend email delivery as part of setup. Invites, password resets, and password-changed security notifications all depend on it.

During development, Dyrected can fall back to an Ethereal preview inbox. That is useful for testing, but it is not a client-ready delivery path. Before handoff:

1. Connect a real email provider.
2. Send one invite to a real inbox.
3. Confirm the recipient sees a clickable link, not a raw token-based workflow unless you intentionally designed it that way.
4. Confirm the recipient can accept the invite and reach the admin.

If email is not configured, the self-hosted admin dashboard now flags that in the **Needs attention** panel so the gap is visible before you hand the system over.

## Permission boundaries to think about early

Before handing the site over, decide:

- who can change schema versus content
- who can publish or only draft
- who should be able to edit shared globals such as navigation and settings

Those decisions do not need to become a full workflow system on day one, but they do need to be explicit. A vague "they will probably only edit pages" is not a permission model.

## Recommended self-hosted path

For most first handoffs:

- keep admin access limited
- use invitations for the first additional admin account
- only mention roles where your self-hosted schema actually exposes them
- test pages, globals, and preview before widening access
- verify email delivery before the handoff meeting

The goal is confidence, not speed.

## Known quick-start edge

Some broader docs in the repo describe a scaffolded auth role set that includes `viewer`. This page keeps the first onboarding path narrower:

- for self-hosted starter output, use the current `admin` and `editor` role shape
- for Cloud, focus on the invitation flow instead of role editing

## Success check

You are ready to call the onboarding setup review-ready when:

- the first admin account works
- one additional editor account can complete a real content task
- the frontend and preview experience behave correctly under that account

At that point, you have moved past setup and into normal product-specific documentation and permission design.
