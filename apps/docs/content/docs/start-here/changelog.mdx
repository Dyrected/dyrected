## v2.26.0

- Explain metrics with `description`.

  - `ViewMetric` and `ViewSubMetric` accept an optional `description`. Cards that have one show an info icon: a tooltip on hover (or keyboard focus) for mouse and trackpad users, and a bottom sheet on touch screens. The choice follows the input device, not the window width.
  - Descriptions support `**bold**`, `*italic*`, `` `code` `` and `[links](https://…)`. Only `http`, `https` and `mailto` links are active, and everything is rendered as React elements, never HTML.
  - Sub-metric descriptions are listed under the card's description in the same tooltip or sheet.
  - `InfoHint` and `InlineMarkdown` are exported from `@dyrected/admin` and `@dyrected/admin/public` so custom React dashboard components can reuse the same behaviour. (`@dyrected/admin`, `@dyrected/core`)

## v2.25.0

- White-label the admin and enforce role menus.

  **Behaviour changes to know about**

  - The admin no longer adds `- Dyrected` to the browser tab title. The suffix is now `meta.titleSuffix` if set, otherwise `- <app name>`, otherwise nothing. Projects that set `titleSuffix` or `branding.logoText` see no change.
  - Transactional emails, the API docs page, the OpenAPI title and the AI assistant no longer name "Dyrected" when no app name is configured. Set `admin.branding.appName` to name your product.
  - Cached navigation preferences are now kept per signed-in user and cleared on sign-out. Previously one user's layout could appear for the next user on the same browser, including items they should not see.
  - A `null` response from the preferences endpoint now resets to the default instead of keeping a stale local copy.

  **New**

  - `admin.branding.appName`, `logoDark`, `logoAlt`, `hidePoweredBy`; `admin.features.systemInfo` / `setupPrompt`; `admin.links.docs`; `admin.strings` for sign-in and storage copy. New helpers `resolveAppName`, `resolveTitleSuffix` and `resolveAdminString` in `@dyrected/core`.
  - Sign-in, first-user and single sign-on screens show the configured logo and app name, and the title and favicon apply before login.
  - Role menus: administrators can design and enforce the sidebar for a role (`admin:navigation-policy`, role scope), and preview any role with `GET /api/admin/navigation?asRole=<role>` (`client.getNavigation({ asRole, raw })`). Menus only narrow `access`, never grant it. Personal layouts cannot add items to an enforced menu.
  - "Role Default" now takes effect: the sidebar reads personal, then role, then global, and publishing a role or global default strips the publisher's pins and own items.
  - `silent` option for `@dyrected/nuxt` to skip the dev-server URL banner.
  - The version lookup only runs for administrators when `features.systemInfo` is on. (`@dyrected/admin`, `@dyrected/core`, `@dyrected/nuxt`, `@dyrected/sdk`)

Both verify the session with `me()` and check the user's role, and both build the SDK client per request so one editor's token is never shared with another request. (`@dyrected/admin`)

- The "Publish as Role Default" dropdown in the navigation editor now lists your project's own roles instead of four fixed names.

  **What was wrong**

  The dropdown only offered `admin`, `editor`, `operator` and `compliance`, so you could not publish a menu for a role like `external`, `finance` or `field_ops` from the admin.

  **What changed**

  - If the role field has no fixed options (for example a free-text or JSON field), the dropdown becomes a text box where you type the role name. **Publish** stays disabled until you enter one.

## v2.24.2

- The Custom Admin Pages guide now says clearly what a page's `access` rule does and does not protect.

  `access` decides who sees a page in the sidebar and who can open it by address. It is not a security boundary, because the page's code ships with the admin. If a page calls an endpoint in your own app, that endpoint has to check who is asking. The guide has a new "Protecting your own endpoints" section with a Next.js route handler that verifies the session with `me()` and checks the user's role. (`@dyrected/admin`)

- The "Role Default" button in the navigation editor now shows for every user the server will accept, not only users whose role is exactly `admin`.

  **What was wrong**

  The server lets `admin`, `super_admin`, `superadmin`, `owner` and the collection's configured admin role publish a navigation layout for a role. The editor only checked for `admin`, so a `super_admin` could never see the button, even though saving would have worked.

  **What changed**

  The editor now uses the same `isUserAdmin` check as the server, so the button and the permission always agree.

## v2.24.1

- The admin no longer shows navigation entries a user can't open. Collections, globals, custom pages, workspaces, views and actions are now hidden when your access rules deny them, and opening one by URL shows a "no access" page instead of the screen.

  **What was wrong**

  Navigation was only filtered by role arrays like `access: ['admin']`. Rules written as functions, Jexl strings or named policies were ignored, so the sidebar listed collections and globals the user couldn't read. View and action access rules were sent to the admin but never used to hide anything, and a global's `access.read` never reached the navigation at all.

  **What changed**

  - `/api/admin/navigation` evaluates every kind of rule with the same resolver the API uses. A rule that throws hides the item. A rule that returns a row-level filter (`{ owner: { equals: user.sub } }`) keeps it visible, because the user can read some rows.
  - `/api/schemas` leaves out views the user can't read, and `/api/admin/navigation/badges` no longer counts items they can't see, including when they've customized their navigation.
  - Workspaces whose views are all hidden disappear, and so do groups left empty.
  - The admin sidebar and routes hide collections, globals and views you can't read, and hide actions you can't run. This uses `access.update`, the rule the server already checks when an action runs.

  This only affects what people see. Your access rules were already enforced by the API, so no data was exposed before and none is newly protected now.

  **Docs fix**

  The `AccessFunction` example used `user.roles contains 'editor'`, but Jexl has no `contains` operator, so that rule always denied. Use `'editor' in user.roles`. (`@dyrected/admin`, `@dyrected/core`)

- Production Nuxt builds no longer return a 500 on `/admin` with `ERR_MODULE_NOT_FOUND` for `react-router/dist/development/dom-export.mjs`.

  **What was wrong**

  `@dyrected/admin` lists `react-router-dom` as a peer dependency, so a server install decides which copy of it you get. On a server with no lockfile (for example when you deploy only one app out of a monorepo), Nitro could leave `react-router` as an external import and then not copy its files into `.output/server/node_modules`. The server started, then failed on the first request to any Admin route. Local builds with a lockfile bundled the router and never showed the problem.

  **What changed**

  `@dyrected/nuxt` now tells Nitro to bundle `react-router` and `react-router-dom` into the server build, so the result no longer depends on how your server lays out `node_modules`. You can remove this workaround from `nuxt.config.ts` if you added it:

  ```ts
  nitro: {
    externals: { inline: [/^react-router(-dom)?($|\/)/] },
  }
  ```

  Rules you already have in `nitro.externals.inline` are kept. (`@dyrected/nuxt`)

## v2.24.0

- A collection or global can now replace its create and edit screens with your own component, while saving still goes through the normal pipeline: validation, access rules, hooks and drafts.

  **For app developers**

  - **Point a collection at a form.** Set `createForm`, `editForm`, or a `form` fallback for both in `admin.components`, then register a component under that key in `components.forms`:

    ```ts
    defineCollection({
      slug: "check_ins",
      admin: {
        components: {
          createForm: "check_ins.scanForm",
          editForm: "check_ins.reviewForm",
          formShell: "header", // "full" (default) | "header" | "none"
        },
      },
    });
    ```

    Globals take `editForm` and `form` the same way. A key that is not registered falls back to the built-in form, so an editor is never left with an empty screen.

  - **Choose how much of the page stays.** `formShell: "full"` keeps the header, status badge and Dyrected's Save bar, so you only re-lay-out the body. `"header"` keeps the header and leaves saving to your form. `"none"` gives your form the whole screen.
  - **Save with `useDocumentForm()`.** It returns the saved `document`, `permissions`, the `form` (values, errors, `setValue`) and `submit()`. `submit({ overrides, redirect, silent })` resolves to `{ ok: true, doc }` or `{ ok: false, errors }` and never throws. Server validation errors land on the matching field, so `useField(path).error` works with no extra code. `redirect` defaults to opening the new record after a create and staying put after an edit.
  - **Reuse the built-in inputs.** `<DyrectedField path="guestName" />`, `<DyrectedFields names={[...]} />` and `<DyrectedDefaultForm exclude={[...]} />` render the real inputs with their labels, conditions, widths, read-only state and `admin.component` overrides.
  - **Relationship drawers use it too.** Creating a related record inline opens the target collection's `createForm` with `presentation: "drawer"`. Set `formInDrawer: false` to keep the built-in form there.
  - **Vue and Nuxt.** `useDocumentForm()`, `DyrectedField`, `DyrectedFields` and `DyrectedDefaultForm` exist in `@dyrected/vue` with state as refs, and work inside a registered form with no manual `provide`.
  - **Safe by default.** A form that throws shows an error card with **Retry** and **Use default form**. `permissions` only decides what to show; the server enforces access on every save.

  **For plugin and integration authors**

  - `@dyrected/core` exports `FormShell`, `DocumentFormComponentSlots` and `GlobalFormComponentSlots`. `collectReferencedComponentKeys` now fills `forms`, so `npx dyrected generate:types` types `Register.componentKeys.forms` and the unused-registration warning covers forms.
  - Config diagnostics report an unknown `formShell` and non-string form keys (source `adminComponents`).
  - `@dyrected/admin/public` exports `DocumentContext`, `DYRECTED_DOCUMENT_KEY` and `buildDocumentFormApi` for hosts that embed the document context.

  **Upgrade notes**

  - `AdminFormComponentProps` changed shape: it is now `{ collection, mode, documentId?, presentation }`. Nothing in Dyrected consumed it before, so this only matters if you typed a placeholder against the old `{ id, readOnly }`.
  - The inline "Create" dialog on relationship fields now saves through the same pipeline as the relationship drawer. A failed save shows an error toast instead of only logging to the console, and a successful one shows a success toast.
  - The hooks and components are marked experimental. (`@dyrected/admin`, `@dyrected/core`, `@dyrected/react`, `@dyrected/vue`)

## v2.23.0

- Custom admin components are now easier to write, harder to get wrong, and no longer need provider boilerplate in Vue.

  **For app developers**

  - **Vue custom components just work.** `useDyrectedForm()`, `useField()`, `useAdminTheme()` and the new `useAdminNavigate()`, `useAdminNotify()` and `useAccess()` work inside any custom field or slot component with no `provideDyrectedForm` call. Prop updates patch the component in place, so local state and input focus are kept.
  - **New hooks and composables.** `useAdminNavigate()` (`navigate` plus `to.collection/document/view/page`), `useAdminNotify()` (`success/error/info`) and `useAccess().can(operation, collection, doc?)` ship in `@dyrected/react` and `@dyrected/vue`. They are marked experimental. `useAccess` is a UI hint only; the server stays authoritative.
  - **Typed component keys.** Run `npx dyrected generate:types` and `defineAdminComponents({ fields: { ... } })` checks your keys against what your schema references. Untyped apps are unaffected.
  - **Better failure modes.** A component that throws shows an inline error card with a Retry button, and the rest of the admin keeps working. This includes errors thrown inside a Vue component. An unregistered key shows a placeholder in development and a warning (a generic placeholder in production).
  - **Unused registrations are flagged.** In development the admin warns once for each registered component the schema never references. Pass `warnUnusedComponents={false}` (or `:warn-unused-components="false"` in Vue) to silence it.
  - **Lazy components.** `React.lazy` and `defineAsyncComponent` components show a skeleton while they load.
  - **Nuxt auto-registration.** Drop a file at `components/dyrected/<registry>/<key>.vue` (for example `components/dyrected/fields/check_ins.scanner.vue`) and it is registered under that key. The `components` prop still wins on a clash, and nothing changes if you don't use the folder.

  **For plugin and integration authors**

  - `AdminComponents` gains `forms`, `viewLayouts`, `pages` and `customComponents`, plus the identity prop types `AdminFormComponentProps`, `AdminViewLayoutProps` and `AdminPageProps`. The first three are declared but not rendered yet; they are reserved for the custom forms, view layouts and pages work.
  - `@dyrected/sdk` exports `RegisteredComponentKeys`, and `Register` accepts `componentKeys`.
  - `@dyrected/core` exports `collectReferencedComponentKeys(schema)`, the scan the CLI and the admin both use.
  - `@dyrected/admin/public` exports `AdminBridgeProvider`, `useAdminBridgeContext`, `AdminComponentErrorBoundary`, `AdminComponentFallback` and the new hooks.

  **Upgrade notes**

  - No breaking changes. Existing registries (`fields`, `dashboard`, `collectionList`, `collectionView`) keep their props.
  - Regenerate types to get `Register.componentKeys`. If you hand-maintain a large `components` map in `admin.vue`, you can move entries into `components/dyrected/<registry>/` one at a time.

- Operational views can now render documents with your own component, while Dyrected keeps the header, KPI metrics, search, pagination, selection, bulk actions and action dialogs.

  **For app developers**

  - **Add a custom layout.** Define a view with `layout: "custom"` and a `component` key, then register a component under that key in `components.viewLayouts`:

    ```ts
    defineView({
      slug: "seating",
      label: "Seating Chart",
      layout: "custom",
      component: "guests.seatingChart",
      options: { tableField: "tableNumber" },
      data: { fetchAll: true },
    });
    ```

  - **Read everything through a hook.** `useCollectionView()` gives you `documents`, `total`, `isLoading`, `pagination`, `sort`, `search`, `filters`, `selection`, `permissions` and `open()`. `useViewActions()` runs the view's actions and shows Dyrected's own confirm dialog and input form. `useGroupedDocuments(field)` groups documents with select and relationship labels resolved. The same three exist in `@dyrected/vue` as composables, with state as refs, and work with no manual `provide`.
  - **Save changes from your layout.** `updateDocument(id, patch)` updates optimistically and rolls back with an error toast if the server rejects the change. Hooks, access rules and validation still run.
  - **Load everything when you need to.** Set `data.fetchAll` to load up to 1,000 documents. Past that, the user sees a notice that the list was truncated.
  - **Safe fallback.** If the component key is not registered, the view shows a message with a **Show as table** button instead of a blank page.

  **Built-in layouts and custom layouts now share one foundation**

  - **Filters everywhere.** Custom layouts get the same filter bar as the table: search, per-field filters and match all/any. Table, kanban, cards and custom layouts now use one implementation, so a filter means the same thing in each.
  - **Slots see the documents.** Components registered in `beforeViewContent`, `afterViewHeader` and the other view slots now receive the documents the active layout loaded, and can call `useCollectionView()`. `documents` was always an empty list before.
  - **Replace a built-in layout.** Register a component under a built-in layout's name, such as `viewLayouts.kanban`, and views with that layout render it in Dyrected's shell, with the same hooks as a custom layout.
  - **One place that describes layouts.** The navigation customizer, the view header icon and the page's dispatch read a single layout registry. `gantt` still renders as a table.

  **For plugin and integration authors**

  - `ViewLayout` gains `"custom"`, and `@dyrected/core` exports `CustomViewConfig`, `CustomViewDataConfig`, `defineCustomView` and `CUSTOM_VIEW_FETCH_ALL_LIMIT`. Views serialized to the admin now carry `component`, `options` and `data`.
  - `@dyrected/admin/public` exports `ViewControllerContext`, `createViewController` and `DYRECTED_VIEW_KEY` for hosts that embed the controller. The controller is subscribable, like the form controller.
  - `npx dyrected generate:types` now includes custom layout components in `Register.componentKeys.viewLayouts`.

  **Upgrade notes**

  - No breaking changes. Existing layouts are untouched.
  - The hooks are marked experimental.
  - If a slot component checked `documents.length === 0` because the list was always empty, it will now see real data.
  - Built-in layouts no longer take `actions`, `onRunAction` and `isRunningAction` props. They read them from the view controller. Only code that rendered `TableLayout`, `KanbanLayout`, `CardsLayout` or `CalendarLayout` directly is affected, and none of them are public exports.
  - A custom view's `component` is required. `defineView` throws at config load if it is missing. (`@dyrected/admin`, `@dyrected/core`, `@dyrected/react`, `@dyrected/vue`)

- Custom pages, view layouts and fields in React can now read and write documents with the editor's own permissions.

  **For app developers**

  - New `useAdminClient()` hook, exported from `@dyrected/react`. It returns the SDK client the admin is already signed in with, so a custom component can call `client.collection("orders").find(...)` or `.update(...)` without handling a token, and only sees what that editor is allowed to see.
  - It is different from `useDyrected()` in `@dyrected/react`, which gives a public site's client and needs its own `DyrectedProvider`. Calling `useDyrected()` inside the admin throws, because the admin does not mount that provider.
  - In Vue, `useDyrectedClient()` already returns the admin's client inside custom components, so nothing changes there.
  - The hook is marked experimental.

  **For integration authors**

  - `useAdminClient` is also exported from `@dyrected/admin/public`. It reads the admin's own context and throws a clear error outside the admin or before sign-in. (`@dyrected/admin`, `@dyrected/react`)

- Your own components inside the admin now keep their styles when your app uses Tailwind v4.

  **For app developers**

  - Before this fix, the admin's stylesheet beat Tailwind v4 utility classes on your own components rendered inside it, because Tailwind v4 puts utilities in a CSS layer and unlayered CSS always wins over layered CSS. A custom field, slot, page or view layout lost its `border`, `bg-*`, `font-bold`, `text-2xl`, `mb-4` and even `ring` or `shadow` classes. The admin now puts its element defaults in `@layer base`, so your classes apply as you wrote them.
  - You no longer need `!important`, inline styles or box-shadow tricks to draw a border inside a custom component.
  - The admin's own appearance is unchanged. Its `dy-*` classes are not layered and still take priority over those defaults.
  - Apps on Tailwind v3 or plain CSS are unaffected, since unlayered host styles already beat layered ones.

  **For integration authors**

  - The scoped reset, the heading, button and field defaults, and the `--tw-*` variable initialisers in `admin.css` are now inside `@layer base`. Layers are supported by all current browsers.
  - Rules that target admin classes, such as `.dy-admin-ui .dy-text-primary`, stay unlayered. (`@dyrected/admin`)

- The development warnings for custom components now actually appear in your app.

  **For app developers**

  - A custom component key that is not registered now shows a placeholder card and a console warning in development, as intended. The same applies to a registered component the schema never references, and to a custom view layout whose component key is missing, which now names the missing key in development.
  - These were switched on by Vite's `import.meta.env.DEV`, which Vite fixes when the admin package is built, so in your app they were always off. They now follow your own `NODE_ENV` and are silent in production builds.
  - The Nuxt `<DyrectedAdmin>` now accepts `warn-unused-components` and passes it through, so `:warn-unused-components="false"` works in Nuxt too.

  **For integration authors**

  - Do not use `import.meta.env.DEV` in code that ships in a library bundle and should follow the host's mode. The admin now has an internal `isDevelopment()` that reads `process.env.NODE_ENV`, which the host's bundler resolves. (`@dyrected/admin`, `@dyrected/nuxt`)

- - **Case-insensitive collection search**: `contains` and `starts_with` now compare lowercased values on MySQL and SQLite, so admin list search no longer depends on letter case (MySQL's binary-collated JSON extraction and SQLite's ASCII-only `LIKE` folding previously made matching case-sensitive). Postgres (`ILIKE`) and MongoDB (`$options: "i"`) were already insensitive.
  - **Literal special characters in search**: `%` and `_` in `contains`/`starts_with` are escaped for SQL `LIKE`, and regex metacharacters are escaped for MongoDB `$regex`, so searching for `50%` or `(` matches literally instead of acting as a wildcard or throwing. The raw `like` operator keeps wildcard semantics on SQL.
  - **Searchable fields chosen by type**: when `admin.searchableFields` is omitted, search covers `admin.useAsTitle` plus every visible `text`, `textarea`, `richText`, `email` and `url` field (up to eight, including fields nested in `row`), regardless of field name. Relationship fields are searched only when listed in `searchableFields`. (`@dyrected/core`)

## v2.22.0

- - **Time-Bucket Grouping on Metric Cards & Sub-Metrics (Phase 3)**:
    - Added object-based `groupBy` support for date fields: `groupBy: { field: string, bucket: "day" | "week" | "month" | "year", limit?: number, orderBy?: "asc" | "desc" }`.
    - Dynamically slices dates into discrete intervals and expands into formatted bucket cards (e.g. `{{group.label}} Tastings` -> `Oct 10, 2026`).
    - Interactive drill-down: Clicking any time-bucket card applies an `isBetween` date interval filter to the active view layout.
    - Zero-N+1 performance: All bucket aggregates and filter conditions resolve in a single batched aggregation request.
  - **Period-over-Period Trend Deltas (Phase 4)**:
    - Added declarative `trend` configuration to `ViewMetric` and `ViewSubMetric`: `trend: { dateField: string, period: "previous_day" | "previous_week" | "previous_month" | "previous_year", invertColors?: boolean }`.
    - Calculates comparative period boundaries (`previous_day`, `previous_week`, `previous_month`, `previous_year`) and computes percentage changes with directional trend badges (`+X% ↑` / `-X% ↓`).
    - Added `invertColors: true` option for metrics where increases indicate risk (e.g. pending tasks, disputes, error counts), displaying positive deltas in rose/alert and negative deltas in emerald.
    - Supports trend deltas on both headline card metrics and individual sub-metric rows.
    - Fan-out optimization: Base values and comparative period aggregates are evaluated together within the single batched query.
  - **Interactive Quick-Filter Distribution Bars & Multi-Layout Compatibility**:
    - Segmented distribution bars with high-contrast luminance stepped palettes and harmonic tonal shading for dark/light modes.
    - Interactive sub-metric chips/tiles allowing click-to-filter drill downs across Table, Kanban, Cards, and Spreadsheet layouts.
    - High-cardinality handling: Top-N groups with an `"Other (X)"` popover drill-down.
  - **React State & Search Params Transition Fixes**:
    - Fixed circular state-searchParams loop on Kanban and Cards layouts preventing "Maximum update depth exceeded" errors when metric cards are toggled as quick-filters. (`@dyrected/admin`, `@dyrected/core`)

## v2.21.0

- - **Metric Scoping Architecture (`metricsScope` & `scope`)**: Added comprehensive filter scoping to operational view metrics and sub-metrics with three evaluation modes:
  - `"view"` (default): Evaluates against the view's persistent filter (`view.filter`), serving as a stable reference KPI unaffected by ephemeral table row filters.
  - `"filtered"`: Dynamically live-syncs with active table toolbar filters, column filters, and search queries.
  - `"collection"`: Evaluates across the entire collection, computing global lifetime totals regardless of view or table filters.
  - Hierarchical inheritance allows views to set `metricsScope`, individual metric cards to specify `scope`, and sub-metric rows to optionally override.
  - **Contextual Scope Icons on Metric Cards**: Added clean, subtle 12px status icons with tooltips (`Filter` for filtered, `Database` for collection, `Layers` for view) next to card headers and sub-metric rows, giving instant visual clarity on data boundaries.
  - **Dynamic Grouped Metrics (`groupBy`)**: Introduced declarative `groupBy` support on `ViewMetric` and `ViewSubMetric`:
    - **Dynamic Metric Cards**: Setting `groupBy: "field"` on a metric card dynamically expands into one metric card per distinct group (e.g. 10 communities $\rightarrow$ 10 cards) with templated labels (`{{group.label}}`, `{{group.value}}`) and group-scoped aggregations.
    - **Dynamic Sub-Metrics**: Setting `groupBy: "field"` on a sub-metric dynamically expands into $N$ breakdown rows in the footer of a single metric card.
    - **Automatic Group Discovery**: Automatically resolves group options for relationship fields (fetching related document titles and IDs), select/radio options, boolean fields, and scalar distinct values.
    - **Single Batched Aggregation**: Fans all dynamically expanded operations across cards, sub-metrics, and groups into a single batched database aggregation query (`client.collection(slug).aggregate(input)`), completely eliminating N+1 queries.
  - **Navigation Editor & Interactive KPI Builder**:
    - Full support in the Navigation Customizer (`ViewMetricsBuilder`) for configuring default view `metricsScope` (`"view" | "filtered" | "collection"`), card `scope`, and `groupBy` (supporting relationship, select, radio, boolean, and scalar fields).
    - Interactive click-to-edit on active KPI chips allowing live reconfiguration of metric labels, operations, target fields, format, colors, scope, and groupBy.
    - Added "Revert View" action in the Navigation Customizer to seamlessly discard personal overrides and restore codebase view definitions.
    - Enhanced `reconcileNavigation` in `@dyrected/core` to intelligently inherit new `metricsScope`, `scope`, `groupBy`, and `subMetrics` from codebase view definitions when sparse user preferences are present.
  - **Native Search Parameter in Operational Views**: Operational views (Table, Cards, Spreadsheet, Kanban) now forward toolbar search directly to the backend pagination endpoint via the `search` query parameter, ensuring performant full-text searches. (`@dyrected/admin`, `@dyrected/core`)
